# OCR 实测结论：本地 OCR 不接入证据链路

测试对象是真实召回的小红书笔记图片，不是构造样本。结论先给：**本地 OCR（rapidocr）
读结构化图片不可靠，不接入链路；只做零成本兜底**。

被否掉的不是“准确率不够高”，而是三条更硬的理由：**结果不可复现、错值静默、置信度不能用来兜底**。
三条任一条成立，读数就不该进事实层；三条同时成立，没有加壳补救的空间。

- 脚本：[`eval/ocr_bench.py`](ocr_bench.py)（`download` 取图 / `run` 识别）
- 语料与原始输出：`eval/forensics/ocr-corpus/`、`eval/forensics/ocr-results.json`
  （已 gitignore，不进仓库；重跑脚本会重新拉取）

---

## 1. 测试方法与核对口径

- 样本：3 条真实召回笔记的 **13 张原图**，覆盖 4 种形态：
  价格表（4 张，含同一张表的两种压缩编码）、尺码/参数表（6 张）、纯文字图（1 张）、
  排版混乱的实拍拼图（1 张）。
- 引擎：`rapidocr_onnxruntime` 1.2.3，PP-OCRv3 det/rec + v2.0 cls，模型随包内置。
- 口径：**按关键字段逐格人工核对**，不看字符准确率。表格每一格（SKU/尺码标签 + 每个数字）
  算一个关键字段；一格漏读或读错即该行不合格；错行/错列单独标注。
- 行还原：按检测框 y 中心聚类成行、行内按 x 排序，模拟“把 OCR 结果整理成表”的最简做法。

## 2. 环境与成本

| 项 | 值 |
| --- | --- |
| 新增依赖体积 | ≈**181 MB**（rapidocr 13.2 + onnxruntime 40.0 + opencv-python 108.6 + Pillow 15.2 + shapely 2.8 + pyclipper/yaml 0.9；numpy 上游已装） |
| 模型 | 3 个 onnx 随包内置（det 2.3 MB / rec 10.2 MB / cls 0.6 MB），无首次下载 |
| 完全离线 | **是**。把 `socket.socket / create_connection / getaddrinfo` 全替换为抛错后仍正常出结果；包内无 HTTP/下载代码 |
| 单图识别 | 0.28–1.05 s，均值 **0.58 s**（1024 px 宽 webp，CPU）；引擎初始化 0.17 s |
| 单图下载 | 0.03–0.04 s（11–37 KB） |

“下载 + 识别”约 **0.62 s/张**，一条笔记读 4 张约 2.5 s。离线与耗时都不是障碍，
问题出在读数本身。

| 指标 | 数值 |

| 漏读单元格 | 53（11.8%）：尺码/SKU 标签 24 个、数字 29 个 |
| 读错单元格（静默错值） | 6（1.3%）：99→66 ×2、<98→86、≤78→$78、围→国 ×2 |

| 乱拍拼图 | 0 可用字段 |

只报 86.8% 会掩盖真正的问题：**一半以上的行拿不出可信数据，且错误不报错**。

## 5. 为什么否掉（三条，按重要性）

### 5.1 不可复现：同一张图，两次结果不同

四时花价格表在两篇笔记里各出现一次，是同一张图、不同压缩编码（11.9 KB / 11.5 KB）：

- 编码 A：`2.0短围裙 | 90 | 138 | 148` —— **漏掉定金 48**；
- 编码 B：`2.0短国裙 | 48 | 90 | 138 | 148` —— **48 读到了**，但 SKU 名「围→国」。

同一份内容、同一个引擎、同一台机器，仅编码不同，一次读到、一次漏掉。
这意味着：**准确率不是这套系统的稳定属性**，无法通过“再跑一遍取多数”来修，
也无法在接入时给出可承诺的准确率。将来任何一次“这次读数对了”的验收都不代表线上行为。

### 5.2 置信度不可用：错值分更高，漏读根本没有分

OCR 每行会返回一个置信度，看起来可以“低于阈值就丢”。实测不成立：

- 天丝 OP 尺码表里，真值 99 被读成 **66**（两处），置信度 **0.649 / 0.639**；
  同一行里读对的 `88` 置信度只有 **0.561**。**错的那个比对的还自信**。
- 漏读的格子**根本不产生输出项**，也就没有任何低分可供过滤。
  例如 `帽子` 行真值 11/68/79/89，输出只有 `79 | 89`——丢掉的 11 和 68 不留痕迹，
  整图平均置信度仍有 0.658（与 100% 正确的简单表 0.715 只差 0.06）。
- 反向噪声反而高分：行内小字「腰饰随JSK赠送」被并成单元格时置信度 **0.844**，
  比它旁边的数字都高。

结论：置信度既不能区分对错，也不能发现缺失，**没有任何阈值能把它变成可用信号**。

### 5.3 静默错值 + 错列：比不读更糟

- 缺失单元格不占位，整行左移。`帽子 79|89` 按列位读会得到“定金 79 / 尾款 89”（真值 11/68）；
  `蝴蝶结头饰 10|15|18` 会被读成“定金 10 / 尾款 15 / 预约价 18”（真值 5/10/15/18）。
- 有 4 处数字是**看着合理的错值**（99→66、98→86），下游无从分辨。
- 行序本身没乱（13 张图无跨行串位），但尺码标签丢了 65%：
  数字在、`XS/S/M/L` 没了，对尺码表等于不可用。
- 乱拍拼图（小红书“实拍出物”的常见形态）0 可用字段。

按“读数错一位比不读更糟”的标准，这套 OCR 不能进链路。

## 6. 后续方向（不接 OCR，零成本兜底）

1. 证据里保留“该帖含 N 张图 + 图片 URL”，回答注明“图中有价格表，文字未解析，请以图为准”。
2. 价格只用正文/评论里出现的数字，不猜图里的值。
3. 若将来一定要接，最多做到“图像类型提示”：用 OCR 判断是否出现“价格表/尺码表”关键词
   （本次 4 张价格表的标题「价格表」全部读对），**不把 OCR 数字写进事实层**。
4. 任何情况下 OCR 结果都要标成「图上文字（OCR，未校验）」并附原图 URL。
