# 多路召回：一源一通道，结果带来源

问答需要的不只是自有知识库：单品身份在 Lolibrary，实时线索在小红书与微博，事实价格在官网。决定：**每个来源是一个独立召回通道，各自只读、互不混写；只在结果层合并，并为每条证据保留来源标注与链接**。核心通道（`own` / `real` / `lolibrary`）每次提问并行召回；补查通道（`xhs` / `weibo` / `web`）由 planner 判断是否追加，不可用时跳过而不是猜。实时通道的结果只作本次回答的临时证据，不落盘、不入索引。公开仓库零语料：只放代码、自有 `content/kb` 与题面。

## Considered Options

- **两源混写一个索引**：召回最高，但证据无法说明出自哪一侧，边界破了查不回来。
- **只吃自有内容**：合规最保守，但把真实语料与实时线索都挡在外面，问答退化。
- **实时结果落本地索引**：检索最强，但 UGC 原文落盘后难追溯授权，且过期内容会长期污染答案。

## Consequences

- planner 的规划对象从「工具」变成「通道」：核心通道固定跑，补查通道按需追加。
- 评测需要可注入的通道替身（mock），否则实时通道不可复现；题面入库、语料不入库。
- Lolibrary 只提供身份与历史信息，不覆盖官网价格与购买链接。
- 关注项依赖具体商品的来源页；实时通道的命中只能提示线索，不能当事实。
